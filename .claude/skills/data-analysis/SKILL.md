# Data Analysis — 20 ปีบนโต๊ะข้อมูลจริง ไม่ใช่ข้อมูลตัวอย่าง

ข้อมูลของ Kambis มาจากคนกรอกมือใน Google Sheets ทุกแถว **ไม่มีชีตไหนสะอาด**
งานนี้จึงไม่ใช่ "แปลงไฟล์เป็นตาราง" แต่คือ **ตัดสินว่าตัวเลขไหนเชื่อได้ และบอกให้ชัดว่าตัวไหนเชื่อไม่ได้เพราะอะไร**

---

## 1. "ประสบการณ์ 20 ปี" แปลว่าพฤติกรรมพวกนี้ ไม่ใช่ตำแหน่ง

1. **ดูไฟล์ดิบก่อนเขียนโค้ดเสมอ** เปิดดู 20 แถวแรกและ 10 แถวท้ายด้วยตา
   โค้ดที่เขียนจากการเดาโครงสร้างจะพังตอนเจอแท็บที่ 3 เสมอ
2. **ไม่เชื่อค่าที่ชีตคำนวณให้** ทุกช่อง Total / % / Index คือ "สิ่งที่คนกรอกเชื่อว่าถูก"
   ไม่ใช่ข้อเท็จจริง — คำนวณใหม่แล้วเทียบ ความต่างคือข้อมูลที่มีค่าที่สุดในงานนี้
3. **แยก "ไม่มีข้อมูล" ออกจาก "ศูนย์" ตลอดชีวิต** `-`, ช่องว่าง, `#DIV/0!` = `null`
   ค่า 0 คือข้อเท็จจริงว่าวันนั้นเก็บได้ 0 กรัม สองอย่างนี้ทำให้ค่าเฉลี่ยต่างกันคนละเรื่อง
4. **ตอบว่า "ยังบอกไม่ได้" ได้โดยไม่รู้สึกผิด** ข้อมูลไม่พอแล้วเดา คือความเสียหายที่แก้ยากกว่าไม่ตอบ
   (เช่น การเบิกวัสดุที่มีเดือนสมบูรณ์เดือนเดียว — ห้ามเทียบแนวโน้ม)
5. **ระบุขอบเขตของตัวเลขทุกครั้ง** "รายได้" ของบริษัท กับ "ยอดขาย" เป็นกรัมรายบรรทัด
   อยู่คนละขอบเขต **ห้ามหารกัน ห้ามบวกกัน** ต่อให้หน่วยดูเข้ากันได้
6. **ตรวจด้วยวิธีที่สองเสมอ** ตัวเลขที่ได้จากทางเดียวคือสมมติฐาน ไม่ใช่ผลลัพธ์ (ดู §6)
7. **เขียน test ทันทีที่ยืนยันค่าได้** ค่าที่ตรวจด้วยมือแล้วไม่ได้ตรึงไว้ใน `tests/` จะถูกทำพังในอีก 2 สัปดาห์

> เกณฑ์ตัดสินใจข้อเดียวที่ใช้ได้ทุกสถานการณ์:
> **ถ้าผู้บริหารเอาตัวเลขนี้ไปตัดสินใจแล้วผิด เราต้องตอบได้ว่ามันมาจากเซลล์ไหนของชีตไหน**

## 2. ลำดับงานมาตรฐาน 7 ขั้น

```
1 สำรวจไฟล์ดิบ      read-any.mjs <ไฟล์> --profile      (§3)
2 ระบุโครงสร้าง      หัวตารางอยู่แถวไหน · คอลัมน์ไหนคือหน่วยอะไร · แถวไหนเป็นยอดรวม
3 แปลงเป็น record    ผ่าน normalize.js เท่านั้น — ห้ามเขียนตัวแปลงวันที่/ตัวเลขตัวที่สอง
4 คำนวณใหม่ทั้งหมด   Σ เอง อย่าอ่านช่อง Total
5 กระทบยอดสองทาง     เทียบกับที่ชีตบอก + เทียบข้ามรายงาน           (§6)
6 ออก finding        ความต่างทุกจุดที่อธิบายไม่ได้ ต้องมีลิงก์ถึง tab + แถว  (§7)
7 ตรึงด้วย test      node --test tests/*.js ต้องผ่านครบก่อนบอกว่าเสร็จ
```

ขั้นที่ 4–6 **ห้ามข้าม** แม้ตัวเลขจะดูสวยแล้ว — ชีตที่สวยที่สุดคือชีตที่คนแก้ตัวเลขให้ตรงด้วยมือ

## 3. อ่านไฟล์ข้อมูลดิบได้ทุกชนิด (Node core ล้วน)

โปรเจกต์นี้ **zero npm dependency** — `node:zlib`, `node:sqlite`, `TextDecoder` เป็น core
จึงอ่าน xlsx/docx/sqlite ได้โดยไม่ผิดกฎ

### เครื่องมือสำรวจ

```bash
node .claude/skills/data-analysis/scripts/read-any.mjs <ไฟล์> [--rows 20] [--profile]
node .claude/skills/data-analysis/scripts/read-any.mjs book.xlsx --sheet "สรุป" --header 6 --profile
node .claude/skills/data-analysis/scripts/read-any.mjs data.json --path sources --json
```

ตรวจให้เอง: ชนิดไฟล์จาก magic bytes · encoding · ตัวคั่น · เซลล์ merge · แท็บทั้งหมด ·
แถวหัวตารางที่เดาได้ · โปรไฟล์รายคอลัมน์ (ไม่ว่าง/ตัวเลข/ผลรวม/min/max/median/ค่าไม่ซ้ำ)

> `--profile` นับ **ทุกแถวรวมแถว Total ของชีต** เป็นตัวเลขไว้สำรวจเท่านั้น
> ยอดจริงต้องมาจาก parser ที่ตัดแถวรวมออกแล้ว

### รองรับอะไรบ้าง

| ชนิด | วิธีอ่าน | สิ่งที่ต้องระวัง |
|---|---|---|
| CSV / TSV / txt | `parseCsv()` ของโปรเจกต์ (RFC4180) | comma ในตัวเลข · `\n` ในเซลล์ · CRLF · BOM |
| Google Sheets | `…/gviz/tq?tqx=out:csv&gid=N` ผ่าน `fetcher.js` | 200 พร้อมหน้า login = "สำเร็จ" ที่ 0 แถว |
| XLSX / XLSM | ZIP → `sharedStrings.xml` + `worksheets/sheetN.xml` | ข้อความอยู่ใน sharedStrings · เซลล์ว่างไม่ถูกเขียนลงไฟล์ · วันที่เป็น serial |
| DOCX | ZIP → `word/document.xml` | ย่อหน้าคือ `<w:p>` · ตารางคือ `<w:tbl>` |
| ODS | ZIP → `content.xml` | `number-columns-repeated` ต้องกาง — **ตัวอ่านยังไม่ผ่านไฟล์จริง** |
| JSON / NDJSON | `JSON.parse` + `--path` | array ของ object ถึงจะเป็นตารางได้ |
| XML / HTML | ดึง `<table>` ด้วย regex | entity ต้อง decode ก่อนเทียบข้อความ |
| SQLite | `node:sqlite` (Node 22+) | เปิดแบบ `readOnly: true` เสมอ |
| **PDF** | **อ่านไม่ได้** | ข้อความอยู่ใน content stream ที่บีบอัด + font map → ขอไฟล์ csv/xlsx แทน **ห้ามคีย์ตัวเลขจาก PDF ด้วยมือไปคำนวณ** |
| **.xls เก่า (BIFF)** | **อ่านไม่ได้** | ให้ Save As เป็น .xlsx/.csv ก่อน |

### สูตรที่ใช้ซ้ำได้ (ตรวจกับไฟล์จริงในโปรเจกต์นี้แล้ว)

```js
// เปิดแพ็กเกจ OOXML ทุกชนิด — ไล่จาก End of Central Directory ย้อนขึ้น
// (ห้ามไล่ local header ทีละอัน: ไฟล์ที่เขียนแบบ streaming ใส่ขนาดไว้ *หลัง* ข้อมูล)
import { unzip } from './scripts/read-any.mjs';

// serial ของ Excel → วันที่ (ฐาน 1899-12-30 เพราะ Excel เชื่อว่าปี 1900 มี 29 ก.พ.)
excelSerialToIso(45000) // → '2023-03-15'
```

### encoding — เดาผิดแล้วภาษาไทยจะกลายเป็นขยะเงียบ ๆ

ลำดับที่ถูกต้อง: **BOM → UTF-8 แบบ `fatal: true` → windows-874 (TIS-620)**
ห้ามใช้ `buf.toString('utf8')` ตรง ๆ กับไฟล์ที่ไม่รู้ที่มา เพราะไบต์ที่ผิดจะกลายเป็น `U+FFFD (�)` เงียบ ๆ โดยไม่ throw
Excel เวอร์ชันไทยเก่ายัง Save CSV เป็น windows-874 อยู่ทุกวันนี้

## 4. กับดักของข้อมูลจริงที่ต้องรู้จักตั้งแต่เห็นไฟล์

| # | อาการ | สิ่งที่ต้องทำ |
|---|---|---|
| 1 | เซลล์ merge → ช่องที่เหลือว่าง | forward-fill (`forwardFill()`) — เจอที่ `sales` (วันที่/ลูกค้า) |
| 2 | หัวตารางกระจาย 2–3 แถว และขึ้นบรรทัดใหม่ในเซลล์ | หาคอลัมน์ด้วย **ตำแหน่ง + ยืนยันด้วยเลขคณิต** ห้าม match ข้อความหัว |
| 3 | หัวคอลัมน์ถูกข้อความอื่นที่ merge ทับ | นับตำแหน่งจากหลักหมุด (`Jan-26` + 11 ช่อง) แล้วยืนยันด้วย Σ12 เดือน = Total |
| 4 | คอลัมน์ซ้ำชื่อ (`XS` กับ `*XS*`) | เลือกตามตำแหน่งเทียบ header มาตรฐาน แล้วออก finding |
| 5 | หน่วยใน label ไม่ตรงค่าจริง (`(Kg)` แต่เป็นกรัม) | เชื่อค่า ไม่เชื่อ label แล้วออก finding `units.*` |
| 6 | แถวยอดรวมปนกับแถวข้อมูล | ตัดออกก่อนรวม แล้วใช้มันเป็น "เฉลย" ไว้กระทบยอด |
| 7 | บรรทัดหมายเหตุใต้ยอดรวมใหญ่ | ตัดทุกแถวหลังยอดรวมใหญ่ในแท็บรายละเอียด (แท็บสรุปห้ามตัด) |
| 8 | ตัวเลขเก็บเป็นข้อความ `"1,695.00"` / `(1,234)` / `1 234` | `num()` — และวงเล็บ = ค่าติดลบแบบบัญชี |
| 9 | ปี พ.ศ. (`01/07/2569`) และปี 2 หลัก | `parseSheetDate()` เท่านั้น **ห้ามเขียนตัวแปลงวันที่ตัวที่สอง** |
| 10 | วันที่พิมพ์ผิดจนอยู่อนาคต (`7 Aug 28`) | parse ได้ แต่ต้องออก finding `dates.future` |
| 11 | แถวลงวันที่ล่วงหน้าที่ยอดถูก carry forward | "ยอดปัจจุบัน" = แถวล่าสุดที่ **วันที่ ≤ วันนี้** ไม่ใช่แถวสุดท้าย |
| 12 | ค่าเกณฑ์เปลี่ยนระหว่างทาง (ขั้นต่ำ 85→38) | อ่านจากแถวเดียวกับที่อ่านยอด ไม่ใช่แถวแรก |
| 13 | แท็บที่เนื้อหาซ้ำกันทั้งแท็บ | จับด้วยลายเซ็นเนื้อหา ไม่ใช่ชื่อ + ให้แท็บที่ชื่อตรงหน้าที่อ่านก่อน |
| 14 | แท็บใหม่ที่ parser อ่านไม่ออก | ต้องได้ finding `structural.tabEmpty` — ห้ามให้ยอดเงียบหาย |
| 15 | ชื่อรายการเขียนไม่ตรงกันสองที่ | normalize ก่อนจับคู่ และ **ถ้าเข้าเค้าหลายรายการ = จับคู่ไม่ได้** (เดาผิดแย่กว่าไม่มี) |

รายละเอียดของแต่ละเคสจริงอยู่ใน `CLAUDE.md` §7 — ทุกข้อในนั้น engine ต้องจับได้

## 5. กฎการคำนวณให้แม่นยำ

### 5.1 เลขทศนิยม

- **ห้ามเทียบ float ด้วย `===`** ใช้ `Math.abs(a - b) <= tol` เสมอ
- **บวกหลายพันแถวต้องชดเชยความคลาดเคลื่อน** — `accurateSum()` (Neumaier) ใน `read-any.mjs`
  การบวกตรง ๆ ทำให้ 0.1+0.2 = 0.30000000000000004 สะสมจนชนกับ tolerance 0.5 g ได้จริง
- **ปัดเศษครั้งเดียวตอนแสดงผล** ห้ามปัดกลางทางแล้วเอาไปบวกต่อ (ปัดสองครั้งได้ค่าคนละตัว)
- ผลรวมต้อง **ไม่ขึ้นกับลำดับการบวก** — ถ้าเรียงข้อมูลใหม่แล้วยอดเปลี่ยน แปลว่าโค้ดผิด

### 5.2 tolerance ที่โปรเจกต์นี้ใช้จริง (`analysis.js`)

| ค่า | ใช้กับ | เหตุผล |
|---|---|---|
| `TOLERANCE_G = 0.5` | ผลรวมน้ำหนัก (กรัม) | ชีตปัดทศนิยม |
| `PCT_TOLERANCE = 0.6` | % ที่คำนวณเทียบกับที่ชีตบอก | % ในชีตปัด 2 ตำแหน่ง |
| `MONEY_TOL = 1` | ยอดเงิน (บาท) | ปัดเศษบาท |
| `CROSS_SOURCE_TOLERANCE_PCT = 2` | ขนออก vs รับเข้า | ของหายระหว่างทาง/ชั่งคนละเครื่อง |
| `0.5` | คงเหลือ/Index ของวัสดุ | หน่วยนับเป็นชิ้น |

**ห้ามขยาย tolerance เพื่อให้ finding หาย** ถ้าความต่างเกินเกณฑ์ แปลว่าชีตมีปัญหาจริง
การขยายเกณฑ์คือการปิดปากเครื่องมือตรวจ ไม่ใช่การแก้ข้อมูล

### 5.3 การหารและค่าเฉลี่ย

- **ตัวหารเป็น 0 หรือ `null` → ผลลัพธ์เป็น `null` ไม่ใช่ 0 ไม่ใช่ `Infinity`**
- **ค่าเฉลี่ยต้องถ่วงน้ำหนัก** — เฉลี่ยของเปอร์เซ็นต์รายวันไม่เท่ากับเปอร์เซ็นต์ของยอดรวม
  ถูกคือ `Σ ส่วน / Σ ทั้งหมด` ผิดคือ `mean(pct_i)`
- **`null` ห้ามนับเข้าตัวหาร** ค่าเฉลี่ยของ 5 แถวที่มีข้อมูล 3 แถว ตัวหารคือ 3
- **เทียบอัตราต่อหน่วยเวลาเมื่อช่วงเวลายาวไม่เท่ากัน** เดือนที่ยังไม่จบเทียบกับเดือนเต็ม
  ต้องเทียบเป็น "ต่อวัน" ไม่งั้นทุกอย่างจะดูตกผิดปกติต้นเดือน
- **ห้ามหารข้ามขอบเขตข้อมูล** — ต้นทุนรายเดือน ÷ ผลผลิตรายเดือน = ต้นทุนต่อกรัม **ทำไม่ได้**
  เพราะต้นทุนเดือนนี้เป็นของครอปที่เก็บเกี่ยวอีกเดือน · รายได้รวม ÷ กรัมที่ขาย = ASP **ทำไม่ได้**
  เพราะรายได้เป็นของทั้งบริษัท ไม่ผูกกับบรรทัดขาย

### 5.4 สถิติ

- ใช้ **median** เป็นจุดอ้างอิงของข้อมูลที่มี outlier ไม่ใช่ mean
- outlier ที่นี่นิยามว่า `> 3 × median` (ออกเป็น `info` ไม่ใช่ `warning` — outlier อาจถูกจริง)
- ข้อมูลน้อยกว่า 2 หน่วยเวลาที่สมบูรณ์ **ห้ามสรุปแนวโน้ม** ให้บอกตรง ๆ ว่าข้อมูลยังไม่พอ
- median ของจำนวนคู่ = เฉลี่ยสองค่ากลาง ไม่ใช่หยิบตัวล่าง

## 6. กระทบยอดสองทาง — ขั้นที่แยกนักวิเคราะห์ออกจากคนเขียน parser

ตัวเลขที่ได้จากทางเดียวคือสมมติฐาน ทุกยอดสำคัญต้องมาจากอย่างน้อยสองทางที่ไม่พึ่งกัน:

| ยอด | ทางที่ 1 | ทางที่ 2 | เกณฑ์ |
|---|---|---|---|
| น้ำหนักดอกต่อแถว | Σ ช่องขนาด XXL…XS | ช่อง `รวม (g)` ในชีต | 0.5 g |
| ยอดต่อแท็บ | Σ ทุกแถวข้อมูล | แถว Total ของแท็บ | 0.5 g |
| ยอดต่อครอป | Σ รายวันจาก `dailyTrim` | ยอดใน `perCrop` | 2% |
| ของถึงปลายทาง | `outbound` ตามวัน | `inbound` ตามวัน | 2% |
| งบรายเดือน | Σ รายการในแท็บรายละเอียด | แท็บ `สรุป` | 1 บาท |
| คงเหลือวัสดุ | คงเหลือเดิม + รับ − เบิก | ช่องคงเหลือในชีต | 0.5 |
| EBIT | EBITDA − ค่าเสื่อม | ช่อง EBIT ในชีต | 1 บาท |

**เมื่อสองทางไม่ตรงกัน ห้ามเลือกข้างเงียบ ๆ** กติกาของโปรเจกต์นี้คือ
แสดงตัวเลขที่ผู้บริหารถืออยู่จริง (แท็บสรุป / ค่าที่คำนวณใหม่แล้วแต่กรณีที่ระบุไว้ใน CLAUDE.md)
แล้ว **ออก finding บอกความต่างพร้อมตัวเลขทั้งสองฝั่ง**

การตรวจชั้นสุดท้ายคือ `verifyPresentation()` — ตัวเลขถูกแต่ **เรียงผิด** ก็ทำให้อ่านผิดได้
ป้ายช่วงเวลาทุกที่ต้องเรียงด้วย `comparePeriod()` ห้าม `localeCompare`

## 7. เขียน finding ให้คนตามไปแก้ได้

```js
{
  id: 'arith.rowTotal', severity: 'critical' | 'warning' | 'info',
  source, tab, gid, row, field,
  messageTh, messageEn,              // ต้องมีครบสองภาษา
  expected, actual, delta,
  related: [{ source, tab, gid }],   // ชีตอื่นที่ต้องเปิดดูประกอบ
}
```

- **ทุก finding ต้องบอกได้ว่า "ไฟล์ไหน › แท็บไหน › แถวที่เท่าไร › ช่องอะไร"**
  ถ้าบอกไม่ได้ แปลว่ายังตรวจไม่เสร็จ ไม่ใช่ finding
- ข้อความต้องมี **ตัวเลขทั้งสองฝั่งกับส่วนต่าง** ("Σ = 67,405 แต่ชีตเขียน 77,405 ต่าง 10,000 g")
  ไม่ใช่ "ผลรวมไม่ตรง"
- การตรวจข้ามรายงาน **ต้องใส่ `related` ครบทุกชีต** ให้ลิงก์เดียวถือว่าไม่ครบ
- `critical` = ตัดสินใจผิดได้ · `warning` = ผิดหลักการแต่เดาเจตนาได้ · `info` = น่าสงสัยแต่อาจถูก
- finding **ไม่บล็อกการแสดงผล** — ข้อมูลยังขึ้นตามปกติ แต่ติดธงกำกับ

สิ่งที่ยัง**ขาด**จนทำ Dashboard ไม่ครบ ไม่ใช่ finding — ไปที่ทะเบียน `public/js/ui/gaps.js`
(คะแนน 100/100 แปลว่า "ตัวเลขที่มีไม่ขัดกันเอง" ไม่ได้แปลว่า "มีตัวเลขครบ")
