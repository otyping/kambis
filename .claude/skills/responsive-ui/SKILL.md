# Responsive UI — มือถือกับ PC ต้องดีคนละแบบ ไม่ใช่แบบเดียวย่อลง

Dashboard นี้ถูกเปิดจากสองที่ที่ต่างกันสุดขั้ว: ผู้บริหารเปิดบนมือถือระหว่างเดินทาง
เพื่อดูตัวเลขไม่กี่ตัว และทีมงานเปิดบนจอใหญ่เพื่อไล่ดูตารางกับกราฟทีละหน้า
**การย่อหน้าจอ PC ลงมาไม่ใช่การออกแบบมือถือ** — สิ่งที่ต้องเปลี่ยนคือลำดับความสำคัญ

---

## 1. หลักที่ตัดสินทุกข้อขัดแย้ง

เรียงตามลำดับ ข้อบนชนะข้อล่างเสมอ:

1. **หาเจอ** — ทุกปลายทางต้องไปถึงได้ และต้องรู้ว่ามันมีอยู่ ของที่ต้องเลื่อนไปเจอเองถือว่าไม่มี
2. **กดถูก** — เป้ากด ≥ 44 × 44 px และห่างกันพอที่นิ้วโป้งจะไม่กดพลาด
3. **อ่านออก** — contrast ผ่าน WCAG AA ทั้งสองโหมด บนพื้นที่สว่างที่สุดของฉากหลัง
4. **สวย** — มาทีหลังสามข้อบน ไม่ใช่ก่อน

> ถ้าดีไซน์ที่สวยกว่าทำให้เมนูข้อ 4–5 หลุดออกนอกจอ ให้ทิ้งดีไซน์นั้น

---

## 2. Breakpoint และสิ่งที่เปลี่ยนในแต่ละช่วง

| ช่วง | ชื่อเรียก | เมนู | grid การ์ด | KPI |
|---|---|---|---|---|
| ≥ 1280px | จอใหญ่ | เมนูสองชั้นเต็มรูป | 3 คอลัมน์ | 6 ช่อง/แถว |
| 768–1279px | แท็บเล็ต | เมนูสองชั้นเต็มรูป | 2 คอลัมน์ | 3 ช่อง/แถว |
| < 768px | มือถือ | **hamburger + แผงเต็มจอ** | 1 คอลัมน์ | 2 ช่อง/แถว |

`767px` คือเส้นเดียวกับที่ JS ใช้ตัดสินใจ (`matchMedia('(max-width: 767px)')` ใน `filters.js`)
**ห้ามตั้งเส้นใหม่ที่ค่าอื่นโดยไม่ย้ายของเดิมตามให้ครบ** ไม่งั้นจะมีช่วงความกว้าง
ที่ CSS คิดว่ามือถือแต่ JS คิดว่า PC แล้ว popup จะไปโผล่ผิดที่

---

## 3. เมนูบนมือถือ — ทำไมต้อง hamburger

**อาการที่ต้องกำจัด:** แถบเมนูที่เลื่อนแนวนอนได้ (`overflow-x: auto`) ดูเหมือนแก้ปัญหา
แต่จริง ๆ คือการซ่อนเมนูข้อท้าย ๆ ไว้นอกจอโดยไม่มีอะไรบอกว่ามันมีอยู่
บนจอ 375px เมนู 5 หน้าจะเห็นแค่ 2–3 หน้าแรก คนที่ไม่เคยใช้จะไม่มีวันรู้ว่ามีหน้า "ต้นทุน"

**กฎ:** เมนูหลักที่มีมากกว่า 3 ปลายทาง บนจอ < 768px ต้องอยู่ใน hamburger ที่เปิดแล้ว
**เห็นทุกปลายทางพร้อมกันโดยไม่ต้องเลื่อน**

โครงที่ใช้ในโปรเจกต์นี้:

```
[☰]  Kambis · ชื่อหน้าปัจจุบัน                    [⟳]     ← แถวเดียว สูง ~56px
```

- กด ☰ → แผงเต็มจอเลื่อนลงมาจากใต้ header (แบบเดียวกับ apple.com)
- ในแผงเรียงตามลำดับความสำคัญ: รายงาน → หน้าย่อย → เครื่องมือ (ธีม/ภาษา/รีเฟรช/ออกจากระบบ)
- **ปิดเองเมื่อ route เปลี่ยน** ไม่งั้นกดเมนูแล้วแผงค้างทับหน้าที่เพิ่งเปิด
- Esc ปิด · กดพื้นหลังปิด · focus trap · คืน focus กลับที่ปุ่ม ☰ (กฎเดียวกับ `modal.js`)
- ล็อก `body` ไม่ให้เลื่อนตอนแผงเปิด แล้วคืนค่าเดิมตอนปิด

**สิ่งที่ต้องไม่ทำ:** ซ่อนเมนูใน hamburger บนจอ PC ด้วย — บนจอกว้างการซ่อนเมนูที่มีที่ว่างให้แสดง
คือการเพิ่มจำนวนคลิกโดยไม่ได้อะไรกลับมา

## 4. Header บนมือถือ: ตัดให้เหลือสิ่งที่ต้องใช้ตอนนั้น

header ของ Dashboard นี้มีของ 7 ชิ้น (โลโก้ · เวลาอัปเดต · คะแนนคุณภาพ · ภาษา · ธีม · รีเฟรช · ผู้ใช้)
บน 375px ถ้าเอาลงมาทั้งหมดจะกินความสูงเกิน 1/4 ของจอก่อนเห็นตัวเลขสักตัว

| ชิ้น | มือถือ |
|---|---|
| โลโก้ + ชื่อ | อยู่ ย่อลง ตัดคำบรรยายใต้ชื่อออก |
| ปุ่มรีเฟรช | อยู่ (เป็นไอคอนอย่างเดียว) — เป็นสิ่งที่กดบ่อยที่สุด |
| ☰ | อยู่ |
| เวลาอัปเดต · คะแนนคุณภาพ · ภาษา · ธีม · ผู้ใช้ | **ย้ายเข้าไปในแผงเมนู** |

ของที่ย้ายเข้าไปห้าม "หายไป" เฉย ๆ — ต้องยังเข้าถึงได้ใน 1 แตะจาก ☰

## 5. เกณฑ์ "เรียบหรู ดูแพง" (อ้างอิง apple.com)

สิ่งที่ทำให้หน้าเว็บ Apple ดูแพงไม่ใช่ลูกเล่น แต่คือ **ความยับยั้งชั่งใจ** 6 ข้อนี้:

1. **ที่ว่างเยอะกว่าที่คิดว่าพอ** ระยะห่างระหว่างกลุ่มต้องต่างจากระยะในกลุ่มอย่างชัดเจน
   (ใช้ `--sp-*` เท่านั้น อย่าใส่ px ลอย ๆ) ถ้าดูแน่น ให้ลบของออก ไม่ใช่ย่อของ
2. **ตัวอักษรมีลำดับชัด ไม่เกิน 4 ขนาดต่อหน้าจอ** หัวข้อใหญ่พอที่จะเป็นหัวข้อจริง ๆ
   ตัวเลขใช้ `font-variant-numeric: tabular-nums` เสมอ เพื่อให้หลักตรงกันทุกแถว
3. **สีเน้นมีสีเดียว** ที่นี่คือเขียว Kambis ทุกอย่างที่เหลือเป็น neutral
   สีที่เพิ่มได้มีแค่ semantic ของ severity — **ห้ามเพิ่มสีเพื่อความสวย**
4. **เส้นบางกว่าเงา** ใช้เส้น 1px กับ `--glass-border-soft` แบ่งพื้นที่ แทนการซ้อนเงาหนา ๆ
   เงาใช้เพื่อบอกระดับความลึกเท่านั้น (มี 3 ระดับ: พื้นหลัง → การ์ด → modal)
5. **การเคลื่อนไหวสั้นและมีเหตุผล** 150–250ms, `ease-out` ตอนเข้า, ไม่มี bounce
   ทุก transition ต้องอธิบายได้ว่าบอกอะไรกับผู้ใช้ ถ้าอธิบายไม่ได้ให้เอาออก
   และต้องหยุดทั้งหมดเมื่อ `prefers-reduced-motion: reduce`
6. **สถานะปัจจุบันต้องเห็นโดยไม่ต้องอ่าน** เมนูที่ active ต่างจากตัวอื่นด้วยน้ำหนัก/พื้น
   ไม่ใช่แค่สีตัวอักษรที่ต่างกันนิดเดียว

**สิ่งที่ทำให้ดูถูกทันที:** ไล่เฉดสีรุ้ง · เงาฟุ้งหลายชั้น · ตัวหนาทุกบรรทัด ·
ไอคอนคนละชุดปนกัน · ขอบมนไม่เท่ากันในหน้าเดียว · ข้อความ ALL CAPS ยาว ๆ ที่ไม่ใช่ป้ายสั้น

## 6. รายการตรวจก่อนบอกว่าเสร็จ

ตรวจด้วย Chrome headless จริง อย่าเชื่อการอ่านโค้ด (unit test จับบั๊กหน้าเว็บไม่ได้)

```bash
# Chrome อยู่ที่ C:\Program Files\Google\Chrome\Application\chrome.exe
chrome --headless=new --remote-debugging-port=9333 --remote-allow-origins=*
# แล้วต่อ WebSocket จาก Node (Node 24 มี WebSocket เป็น global — ไม่ผิดกฎ zero dependency)
```

ทุกข้อต้องผ่านทั้ง **โหมดสว่าง/มืด** และ **ไทย/EN**:

- [ ] `Runtime.exceptionThrown` ต้องไม่มีเลย
- [ ] canvas ทุกตัว `width > 0` (ถ้าเป็น 0 = กราฟไม่ถูกวาดแต่ไม่มี error)
- [ ] `documentElement.scrollWidth - clientWidth === 0` ที่ 375 / 768 / 1280 / 1920px
- [ ] ทุกปลายทางในเมนูกดถึงได้จากจอ 375px โดยไม่ต้องเลื่อนแนวนอน
- [ ] ปุ่มทุกปุ่มบนจอ 375px มี `getBoundingClientRect()` สูง ≥ 44px
- [ ] เปิดแผงเมนูแล้วกด Tab วนอยู่ในแผง · Esc ปิดได้ · focus กลับที่ปุ่มเดิม
- [ ] สลับหน้าแล้วแผงปิดเอง
- [ ] ย่อ/ขยายจอระหว่างที่แผงเปิดอยู่แล้วไม่มีอะไรค้าง

**กับดักตอนยิง event ผ่าน CDP:** listener ที่ผูกกับ element (ไม่ใช่ `document`)
จะไม่ได้รับ event ที่ `document.dispatchEvent()` เพราะ event bubble ขึ้นอย่างเดียว
ต้องยิงจาก `document.activeElement` — เคยทำให้สรุปผิดว่า Esc ใช้ไม่ได้ทั้งที่โค้ดถูก

## 7. ข้อจำกัดของโปรเจกต์ที่ยังใช้อยู่

- Vanilla JS + zero dependency (Three.js เป็นข้อยกเว้นเดียว vendor ไว้แล้ว)
- **ห้ามฮาร์ดโค้ดสีนอก `tokens.css`** ทุกค่าอ้างผ่าน custom property
- ทุกข้อความ chrome ต้องมีคีย์ครบสองภาษาใน `public/js/i18n.js`
- `hidden` ที่ชนกับคลาสที่ตั้ง `display` ต้องเขียน `.x[hidden]{display:none}` กำกับเสมอ
  (specificity เท่ากัน คลาสที่มาทีหลังชนะ — เมนู Dryflower เคยโผล่ค้างบนหน้า Supply เพราะเหตุนี้)
- ห้ามเก็บหน้าไว้ใน DOM แล้วสลับด้วย `hidden` — `setupCanvas()` คืน `null` เมื่อกว้าง 0
  แล้วกราฟจะ bail เงียบ ๆ (ดูลำดับ 5 ขั้นใน CLAUDE.md §6.5)
